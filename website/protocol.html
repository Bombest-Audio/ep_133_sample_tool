The EP-133 file & playback SysEx protocol.

Everything we figured out getting samples on and off the K.O. II. There's no spec sheet for this, so we wrote one — all of it pulled straight off real hardware and cross-checked against TE's own web tool. This one's for the community, from Bombest Audio.

MFR  00 20 76 DEVICE  0x33 SUBSYS  0x40 CHUNK  512 B

01 Transport

The K.O. II shows up as a plain USB-MIDI device — no driver, no app, nothing to install. On macOS it lands in CoreMIDI as EP-133. If your DAW can see it, so can this.

Two totally separate things ride that one port. The pads just send ordinary MIDI notes — 36–83, spread across the four groups A / B / C / D. That part's easy. Everything else — the filesystem, uploads, playback — is SysEx only. There's no CC or note that loads a WAV. It all rides the frames below.

03 7-bit packing

SysEx data bytes only carry 7 bits — the top bit is off-limits. So to move real 8-bit bytes, the device packs them LSB-first: one high-bits byte holds the 8th bit of the next seven data bytes, where bit k of that high-bits byte belongs to data byte k.

unpack · per byte
// LSB-first: high bit of data[k] lives in bit k of highbits
unpacked[k] = (data[k] & 0x7F) | (((highbits >> k) & 1) << 7);

Flip the bit order and everything past 0x7F gets quietly mangled — your WAV header reads fine and the audio comes out garbage. It's LSB-first. Not MSB-first (gotcha #2).

04 Handshake

Greet (command 1) is the hello. You get back an ASCII key/value string — product, firmware, serial — so you know you've got the right unit and can read its real device id.

greet · command 1 · response payload
product=EP-133 firmware=2.0.5 serial=KO2xxxxxxxx

Before any file op, you've got to open a session. That's command 5, subcommand FILE_INIT (1). It negotiates a 512-byte chunk size and sets up the session you'll lean on for the rest of the transfer. Skip it and every file op just fails.

05 File subcommands

All the file and playback work lives under command 5. The first payload byte picks the subcommand. (It's 5 — not 127. See gotcha #1.)

SubcommandCodeDoes
FILE_INIT1Open a file session, negotiate chunk size.
FILE_PUT2Upload a file — the WAV import path.
FILE_GET3Download a file off the device.
FILE_LIST4List children of a node.
FILE_PLAYBACK5Trigger playback of a node.
FILE_DELETE6Delete a node.
FILE_METADATA7Read/write a node's metadata blob.
FILE_INFO11Size, type, status of a node.

06 Node tree

The filesystem is a tree of numbered nodes, all hanging off root 0. Your samples live under sounds (1000) as sequential .pcm slots; your saved work lives under projects (2000), and every project carries a groups directory split into pad groups A / B / C / D.

0 root
├─ 1000 sounds // sample slots
│ ├─ 1001 001.pcm
│ ├─ 1002 002.pcm
│ └─ … … sequential node ids
└─ 2000 projects
├─ 3000 project 01
│ └─ groups
│ ├─ A ├─ B ├─ C └─ D
├─ 4000 project 02
├─ … … (5000, 6000 …)
└─ 11000 project 09

Projects step by 1000: 01→3000, 02→4000, … 09→11000. Every project's groups dir exposes A / B / C / D.

07 FILE_PUT upload sequence

This right here is the whole reason the tool exists. Getting a WAV onto the device is a strict handshake — every step waits on the one before it. Rush it and you get "unexpected page" back, or worse, the device wedges (gotcha #4).

1

Open session

FILE_INIT to negotiate the 512-byte chunk size and a fresh session.

cmd 5 · sub 1
await OK
2

Resolve /sounds

Locate the sounds directory — node 1000 — as the upload target.

node 1000
3

PUT INIT

Announce the file. The device assigns a fileId — wait for it, you'll need it on every page.

cmd 5 · sub 2
await fileId
4

Paged DATA

Stream the file in ~427-byte chunks. Each page gets a unique request id, and you wait for that page's ack before sending the next.

~427 B / page
await each ack
5

Zero-length terminator

Send an empty final page. This commits the file. Forget it and the device stays wedged until power-cycle.

len 0
await OK

512 bytes is the wire size; once you take out the high-bits packing overhead, each page carries ~427 bytes of actual file data.

08 Gotchas

Every single one of these cost us time. Read 'em before you write a byte.

#0

Pull the STATUS byte off first. Responses tuck a status code in after the command. Unpack before you strip it and your whole payload slides over by one.

#1

File ops are command 5, not 127. 127 looks like the obvious "system" command. It's not the one. Everything filesystem lives under 5.

#2

Packing is LSB-first. Bit k of the high-bits byte maps to data byte k. Decode it MSB-first and you get garbage that looks just right enough to fool you.

#3

Wait for every ack. Fire pages off without waiting and you'll get "unexpected page". One page out, one ack in, then the next. No rushing.

#4

Always send the terminator. Leave a PUT half-finished and the device wedges — it goes quiet until you power-cycle it. Send that zero-length final page no matter what, even when you're bailing out.

#5

Pack every multi-byte field. Node ids, file ids, lengths — anything bigger than 7 bits gets 7-bit packed too. No exceptions.

11 Reproduce it

Don't take our word for it. Grab sendmidi and receivemidi you can greet a real unit straight from the terminal. syx wants the bytes between F0 and F7, in decimal.

macOS terminal · greet (command 1)
# listen on one tab
receivemidi dev "EP-133" syx

# send the greet on another
#        00 20 76  33  40  60  00  01   (hex)
sendmidi dev "EP-133" syx 0 32 118 51 64 96 0 1

# reply comes back as ASCII key/values:
# product=EP-133 firmware=2.0.5 serial=KO2…

96 is flags 0x60 = is-request + request-id-present. 0 is the request id, 1 is Greet.
