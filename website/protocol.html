The EP-133 file & playback SysEx protocol.

Everything we learned dragging samples on and off the K.O. II. No spec sheet exists, so we wrote one. Captured live off real hardware, cross-checked against TE's own web tool. This one's for the community — from Bombest Audio.

MFR  00 20 76 DEVICE  0x33 SUBSYS  0x40 CHUNK  512 B

01 Transport

The K.O. II shows up as a plain class-compliant USB-MIDI device — no driver, no app. On macOS it enumerates in CoreMIDI under the name EP-133. If your DAW can see it, this tool can talk to it.

Two completely separate things ride that one MIDI port. Pads send ordinary MIDI notes — notes 36–83, mapped across the four pad groups A / B / C / D. Everything else — the filesystem, sample upload, playback triggers — is SysEx only. You will not find a CC or a note that uploads a WAV. It all goes through the frames below.

03 7-bit packing

SysEx data bytes can only carry 7 bits — the high bit is reserved. To move real 8-bit bytes, the device packs them LSB-first: a single high-bits byte carries the 8th bit of the next up-to-7 data bytes, with bit k of the high-bits byte belonging to data byte k.

unpack · per byte
// LSB-first: high bit of data[k] lives in bit k of highbits
unpacked[k] = (data[k] & 0x7F) | (((highbits >> k) & 1) << 7);

Get the bit order wrong and every byte past 0x7F is silently mangled — your WAV header looks fine and the audio is garbage. It is LSB-first. Not MSB-first (gotcha #2).

04 Handshake

Greet (command 1) is the hello. It returns an ASCII key/value string — product name, firmware, serial — so you can confirm you're talking to the right unit and read its real device id back.

greet · command 1 · response payload
product=EP-133 firmware=2.0.5 serial=KO2xxxxxxxx

Before any file operation you must open a file session. File session init is command 5 with subcommand FILE_INIT (1). It negotiates a 512-byte chunk size and hands back a session you'll reference for the rest of the transfer. Skip it and every file op fails.

05 File subcommands

All file and playback work lives under command 5. The first payload byte picks the subcommand. (It is command 5 — not 127. See gotcha #1.)

SubcommandCodeDoes
FILE_INIT1Open a file session, negotiate chunk size.
FILE_PUT2Upload a file — the WAV import path.
FILE_GET3Download a file off the device.
FILE_LIST4List children of a node.
FILE_PLAYBACK5Trigger playback of a node.
FILE_DELETE6Delete a node.
FILE_METADATA7Read/write a node's metadata blob.
FILE_INFO11Size, type, status of a node.

06 Node tree

The filesystem is a tree of numbered nodes. Everything hangs off root 0. Samples live under sounds (1000) as sequential .pcm slots; saved work lives under projects (2000), each project carrying a groups directory split into pad groups A / B / C / D.

0 root
├─ 1000 sounds // sample slots
│ ├─ 1001 001.pcm
│ ├─ 1002 002.pcm
│ └─ … … sequential node ids
└─ 2000 projects
├─ 3000 project 01
│ └─ groups
│ ├─ A ├─ B ├─ C └─ D
├─ 4000 project 02
├─ … … (5000, 6000 …)
└─ 11000 project 09

Projects step by 1000: 01→3000, 02→4000, … 09→11000. Each project's groups dir always exposes A / B / C / D.

07 FILE_PUT upload sequence

This is the whole reason the tool exists. Getting a WAV onto the device is a strict handshake — every step waits for the one before it. Rush it and the device throws "unexpected page", or worse, wedges (gotcha #4).

1

Open session

FILE_INIT to negotiate the 512-byte chunk size and a fresh session.

cmd 5 · sub 1
await OK
2

Resolve /sounds

Locate the sounds directory — node 1000 — as the upload target.

node 1000
3

PUT INIT

Announce the file. The device assigns a fileId — wait for it, you'll need it on every page.

cmd 5 · sub 2
await fileId
4

Paged DATA

Stream the file in ~427-byte chunks. Each page gets a unique request id, and you wait for that page's ack before sending the next.

~427 B / page
await each ack
5

Zero-length terminator

Send an empty final page. This commits the file. Forget it and the device stays wedged until power-cycle.

len 0
await OK

The 512-byte chunk is the wire size; after the high-bits packing overhead each page carries ~427 bytes of real file data.

08 Gotchas

Every one of these cost us time. Read them before you write a byte.

#0

Consume the STATUS byte first. Responses insert a status code after the command. Unpack before you strip it and your whole payload shifts by one.

#1

File ops are command 5, not 127. 127 looks like a tempting "system" command. It isn't the file subsystem. Everything filesystem lives under 5.

#2

Packing is LSB-first. Bit k of the high-bits byte maps to data byte k. MSB-first decoding gives you plausible-looking garbage.

#3

Await every ack. Fire pages without waiting and you get "unexpected page". One page out, one ack in, then the next.

#4

Always send the terminator. An incomplete PUT wedges the device — it stops responding until you power-cycle it. Send the zero-length final page, even on abort.

#5

Pack every multi-byte field. Node ids, file ids, lengths — anything wider than 7 bits is itself 7-bit packed. No exceptions.

11 Reproduce it

Don't take our word for it. With sendmidi and receivemidi you can greet a real unit from a terminal. syx takes the bytes between F0 and F7, in decimal.

macOS terminal · greet (command 1)
# listen on one tab
receivemidi dev "EP-133" syx

# send the greet on another
#        00 20 76  33  40  60  00  01   (hex)
sendmidi dev "EP-133" syx 0 32 118 51 64 96 0 1

# reply comes back as ASCII key/values:
# product=EP-133 firmware=2.0.5 serial=KO2…

96 is flags 0x60 = is-request + request-id-present. 0 is the request id, 1 is Greet.
